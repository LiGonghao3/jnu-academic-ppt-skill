# 叙事骨架与页数规划

## 核心原则：标题准确说明这页的任务

结果、比较和判断页优先使用有证据支持的结论标题；背景、定义、实验设置和流程页用直接的主题标题更自然。不要为了“像结论”而提前下判断。

| ✗ 话题式标题 | ✓ 结论式标题 |
|---|---|
| 实验结果分析 | 掉点来自数据增强，不是模型 |
| 相关工作 | 现有三类方法都绕不开标注成本 |
| 本周工作 | Baseline 跑通了，但复现差 6.8 个点 |
| 下一步计划 | 下周先对齐评测口径，再动模型 |
| 数据集介绍 | 我们的数据比公开集多 3 倍长尾类别 |

读者扫一眼标题就该知道这页讲什么或得出了什么。结果页正文是证据；设置页正文是边界和口径。
**一页只承担一个主要任务**；两个互不依赖的任务通常应拆开。

## 时长 → 页数

一页一分钟只用于初步估算。方法总图、复杂实验图可能需要 1.5–2 分钟；封面、目录和章节页虽然讲得快，仍会打断节奏并占用总页数。

| 时长 | 总页数 | 其中内容页 | 章节数 |
|---|---|---|---|
| 5 分钟 | 7–9 | 4–6 | 2–3 |
| 10 分钟 | 11–14 | 7–10 | 3–4 |
| 15 分钟 | 16–20 | 11–15 | 4–5 |
| 20 分钟 | 21–26 | 15–20 | 4–5 |

章节别超过 5 个。`jnu-defense` 和 `jnu-rigor` 的顶部导航最多放 5 项，
`jnu-teal` 的左侧导航最多 6 项，超了会挤。

### 短组会紧凑模式

10 分钟以内默认不单独放目录和章节过渡页，只在页眉/导航中标章节。推荐结构：封面、7–9 张内容页、结尾。使用本地引擎时，写了 `meta.duration_minutes` 且不超过 10 分钟就会自动进入紧凑模式（也可以直接写 `meta.presentation_mode: "compact"`），构建器会保留章节归属但跳过 `toc` 和 `section` 页面。

答辩、开题或 15 分钟以上的正式报告可以保留目录和 3–5 个章节过渡页。

## 各场景骨架

### 每周组会 / 进展汇报

```
封面
目录
├─ 一 本周主线          ← 50% 篇幅，最重要的那件事
│   · 结论页（一句话说清这周最大的发现/进展）
│   · 证据页（数字、图、表）
│   · 过程页（怎么做的，可选）
├─ 二 其他进展          ← 比赛、读的文章、听的报告、杂事，每件 1–2 行
├─ 三 卡点与求助        ← 必须单独成章，不要藏
│   · 2–4 个问题，每个写清「卡在哪 + 想要什么帮助」
└─ 四 下周计划          ← 具体到天或到可交付物
结尾
```

**卡点章是组会的核心价值**。很多人把它写成一行「遇到一些困难」，
那整场会就白开了。每个卡点要写清三件事：卡在哪、试过什么、想要谁给什么。

### 论文精读

```
封面（论文标题 + 出处 + 年份）
目录
├─ 一 它解决什么问题     ← 问题是什么 + 之前怎么做 + 差在哪
├─ 二 怎么做的           ← 核心方法，一张图讲清楚
├─ 三 证据              ← 用原文的图表，标出处
├─ 四 我的评价           ← 哪里信、哪里不信、有什么没说清
└─ 五 对我们的启发       ← 不可省略，这是汇报的意义
结尾
```

### 开题 / 中期答辩

```
封面（题目 / 答辩人 / 导师 / 学院专业 / 日期）
目录
├─ 一 选题背景与意义
├─ 二 研究内容与目标
├─ 三 技术路线与方法     ← 最好有一张技术路线图
└─ 四 进度安排与预期成果
结尾（致谢）
```

### 毕业论文答辩

```
封面
目录
├─ 一 选题背景与意义
├─ 二 研究方法与过程
├─ 三 研究成果与展示     ← 篇幅最大，放主要结论和数据
└─ 四 总结、不足与致谢   ← 主动说不足，比被问出来好
结尾
```

### 竞赛路演

```
封面（项目名 + 一句话价值主张）
├─ 一 痛点              ← 谁在痛、痛到什么程度，最好有数
├─ 二 我们的方案
├─ 三 核心亮点           ← 对着评分标准写
├─ 四 验证与成果         ← 数据、用户、奖项、专利
└─ 五 落地规划与团队
结尾
```

## 版式选择的经验规则

| 内容形态 | 用哪个版式 |
|---|---|
| 一个结论 + 3–5 条支撑 | `bullets`（配 `lead` 写结论） |
| 两件事对着比 | `compare`（前后、我们 vs 别人） |
| 并列的 2–4 个点，彼此独立 | `cards` |
| 有先后顺序的流程 | `steps` |
| 按时间排的计划或历程 | `timeline` |
| 2–4 个关键数字 | `kpi` |
| 随类别或时间变化的真实数值 | `chart`（原生可编辑，必须写单位和来源） |
| 有图必须配解释 | `image-text` |
| 一张大图就是全部 | `image-full` |
| 多行多列的对比数据 | `table`（不超过 6 行 4 列） |
| 一句话的教训 / 金句 / 结论 | `quote` |
| 两组平行的要点 | `two-col` |

**别滥用 cards**。三张卡片看起来整齐，但如果三件事其实是有顺序的，
用 `steps`；如果是平行要点，`bullets` 往往更好读。

## 常见毛病

- **每页都是 bullets**：一份 12 页的 PPT 里至少要有 3 种不同版式，否则听众会困
- **没有结论页**：光有过程没有结论，听完不知道你想说什么
- **卡点写得太客气**：「可能还需要进一步探索」等于没说
- **计划不落地**：「继续优化模型」是废话，「周三前把评测口径对齐到切片级」才是计划
- **图没有解释**：放一张实验结果图但不说要看哪里，等于没放
- **致谢页写得敷衍**：答辩场景里致谢是有分的，具体到人和事
